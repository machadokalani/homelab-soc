# Setup do Ambiente — VM Windows 10 (Alvo)

## Objetivo

Com a base em Linux já configurada, o próximo passo foi criar uma segunda VM rodando Windows 10 para atuar como máquina alvo dentro do laboratório. Essa VM vai gerar os eventos que o Wazuh vai coletar e analisar — é o ponto de origem da telemetria que sustenta todo o pipeline de detecção que está sendo construído. Diferente da VM Ubuntu, aqui o objetivo não é aprender o sistema operacional em si, mas sim ter um ambiente Windows realista o suficiente para simular atividade de endpoint (processos, conexões de rede, logins) que um SOC precisaria monitorar.

## Ambiente

**Hypervisor:**
- VirtualBox

**Sistema operacional da VM:**
- Windows 10 (ISO oficial da Microsoft, sem chave de produto)
- Escolhido por ser ainda amplamente usado em ambientes corporativos no Brasil, o que torna a experiência de detecção mais aplicável a cenários reais de SOC júnior

**Recursos alocados à VM:**
- RAM: 4096 MB
- CPUs: 2
- Disco: 50 GB (dinâmico)

**Rede:**
- Adaptador 1: NAT (acesso à internet para updates e ferramentas)
- Adaptador 2: Rede exclusiva de hospedeiro / Host-Only (vboxnet0), na faixa 192.168.56.0/24
- IP estático definido manualmente no adaptador Host-Only: 192.168.56.20

## Processo

### 1. Criação da VM

Criei a VM com nome "windows10", tipo Windows, versão 64-bit, seguindo a mesma lógica de alocação de recursos da VM Ubuntu, mas com RAM um pouco maior (4096 MB) considerando que o Windows 10 e, futuramente, o Sysmon e o agente Wazuh rodando juntos consomem mais memória do que um Ubuntu server básico.

### 2. Configuração de rede dupla

Configurei os dois adaptadores de rede: NAT no Adaptador 1 para a VM ter internet, e Host-Only (vboxnet0) no Adaptador 2 para o tráfego isolado do laboratório, seguindo o mesmo padrão de rede já usado nas outras VMs. O IP estático 192.168.56.20 foi definido manualmente no adaptador Host-Only, fora da faixa de DHCP, para manter consistência com a documentação e com o IP fixo do Wazuh manager (192.168.56.5).

### 3. Troubleshooting: travamento recorrente durante a instalação

Durante a instalação, a VM travava repetidamente em pontos diferentes do processo. A janela da VM parava de responder completamente (mouse e teclado sem efeito), mas o host continuava respondendo normalmente fora da janela do VirtualBox.

A primeira hipótese testada foi o conflito entre VBS (Virtualization Based Security) do Windows host e o acesso do VirtualBox à VT-x. Desativar a Integridade da Memória (Memory Integrity/Core Isolation) no host reduziu parte do problema, mas os travamentos continuaram acontecendo, agora de forma mais esporádica.

O padrão que confirmou a causa raiz real foi: pausar e despausar a VM travada destravava o processo imediatamente, sem qualquer perda de progresso. Esse comportamento específico é característico de um stall no agendamento de vCPU/timer, não de um travamento real do sistema — e é um problema conhecido em CPUs Intel de arquitetura híbrida (núcleos de Performance + núcleos de Eficiência, presentes a partir da 12ª geração) rodando VirtualBox. O agendador do Windows host ocasionalmente realoca as threads da VM entre P-cores e E-cores, e o VirtualBox, ao usar o provider de paravirtualização padrão (que assume um modelo baseado em Hyper-V), não lida bem com essa troca no meio da execução, interrompendo momentaneamente o clock virtual da VM.

A correção foi trocar o provider de paravirtualização da VM de `default` para `kvm`, via linha de comando (VBoxManage), com a VM desligada:

```
VBoxManage modifyvm "windows10" --paravirtprovider kvm
```

A confirmação de que a mudança foi aplicada corretamente foi feita com:

```
VBoxManage showvminfo "windows10" | Select-String "paravirt"
```

retornando `Paravirt. Provider: KVM` e `Effective Paravirt. Prov.: KVM`. Após essa mudança, a instalação prosseguiu sem novos travamentos.

## Lições Aprendidas

- **Memory Integrity vs. Hyper-V**: desativar a Integridade da Memória no host resolve o conflito de VBS pelo acesso à VT-x, mas não desliga o Hyper-V em si — são camadas relacionadas, porém distintas, e ambas podem competir com o VirtualBox por recursos de virtualização de hardware.

- **Diagnóstico por comportamento, não só por sintoma**: travamentos em pontos aleatórios do processo, que se resolvem com pausa/retomada e não afetam o host, são um padrão de diagnóstico específico (stall de scheduling), diferente de um travamento genuíno do sistema. 

- **CPUs híbridas e paravirtualização**: processadores Intel com núcleos de Performance e Eficiência (12ª geração em diante) podem ter conflitos com o provider de paravirtualização padrão do VirtualBox em VMs Windows. Trocar para o provider KVM (`--paravirtprovider kvm`) contorna esse problema ao mudar como a VM sincroniza clock e agendamento com o processador host.

- **`--paravirtprovider`**: parâmetro do VBoxManage que define qual interface de paravirtualização a VM usa para se comunicar com o hypervisor subjacente. O valor `default` costuma assumir um modelo Hyper-V quando detecta um guest Windows; `kvm` força um modelo alternativo, geralmente mais estável em hardware com núcleos híbridos.

- **Configuração isolada por VM**: alterações feitas via VBoxManage em uma VM específica (como o paravirtprovider) não afetam o host nem outras VMs — ficam salvas no arquivo de configuração daquela VM individualmente, da mesma forma que RAM, CPU ou adaptadores de rede.
