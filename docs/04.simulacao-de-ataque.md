# Simulação de Ataque com Atomic Red Team — Validação da Pipeline de Detecção

## Objetivo

Validar a pipeline de detecção existente (Sysmon → Wazuh Agent → Wazuh Manager → Dashboard) através da simulação de uma técnica real de ataque (MITRE ATT&CK).

## Ambiente

- **wazuh-manager** (192.168.56.5): Wazuh 4.14, indexer + server + dashboard, operacional.
- **Windows 10** (192.168.56.20, hostname `DESKTOP-OBOJBDU`): Sysmon (config SwiftOnSecurity) e Wazuh Agent ativos.
- **Framework de simulação**: Invoke-AtomicRedTeam v2.1.0.
- **Técnica testada**: MITRE ATT&CK **T1059.001** (Command and Scripting Interpreter: PowerShell), teste específico **T1059.001-17** ("PowerShell Command Execution" — exemplo do Threat Detection Report 2021 da Red Canary).

## Processo

### 1. Instalação do Invoke-AtomicRedTeam

Política de execução ajustada apenas para a sessão ativa, evitando alterar a configuração de segurança da máquina de forma permanente:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Instalação do framework e download da biblioteca de testes:

```powershell
IEX (IWR 'https://raw.githubusercontent.com/redcanaryco/invoke-atomicredteam/master/install-atomicredteam.ps1' -UseBasicParsing)
Install-AtomicRedTeam -getAtomics
```

Carregamento do módulo na sessão:

```powershell
Import-Module "C:\AtomicRedTeam\invoke-atomicredteam\Invoke-AtomicRedTeam.psd1" -Force
Get-Command Invoke-AtomicTest
```

Confirmado: `Invoke-AtomicTest`, versão `2.1.0`, módulo `Invoke-AtomicRedTeam`.

### 2. Conflito com o Windows Defender

Ao tentar inspecionar o primeiro teste (`Invoke-AtomicTest T1059.001 -ShowDetails`), o PowerShell retornou erro:

```Get-Content : Não foi possível concluir a operação com êxito porque o arquivo contém
um vírus ou software possivelmente indesejado.
No C:\AtomicRedTeam\invoke-atomicredteam\Public\Get-AtomicTechnique.ps1:94 caractere:28
CategoryInfo : ReadError: (C:\AtomicTea...T1059.001.yaml:String) [Get-Content], IOException
FullyQualifiedErrorId : GetContentReaderIOError,Microsoft.PowerShell.Commands.GetContentCommand
```

O Defender bloqueou a leitura dos arquivos YAML de definição de teste — comportamento esperado, já que esses arquivos descrevem literalmente padrões de ataque (o `Get-MpThreatDetection` confirmou detecções em múltiplas técnicas, não só T1059.001, incluindo arquivos da técnica **T1218.011**, ex: `atomics\T1218.011\src\...` e `bin\_WT.init`). Isso mostrou que o Defender varre a pasta de atomics como um todo, não reage a uma técnica específica.

Resolução — exclusão de pasta completa (mais sustentável do que liberar arquivo por arquivo a cada nova técnica testada) e reinstalação dos atomics já quarentenados:

```powershell
Add-MpPreference -ExclusionPath "C:\AtomicRedTeam"
Get-MpPreference | Select-Object -ExpandProperty ExclusionPath
Install-AtomicRedTeam -getAtomics -Force
```

Após a exclusão, `Invoke-AtomicTest T1059.001 -ShowDetails` passou a funcionar.

### 3. Seleção do teste

Optou-se pelo **teste #17 — "PowerShell Command Execution"**, por não depender de payload externo e ser determinístico.

Detalhes do teste (`Invoke-AtomicTest T1059.001-17 -ShowDetails`):

```Atomic Test Name: PowerShell Command Execution
Atomic Test Number: 17
Description: Use of obfuscated PowerShell to execute an arbitrary command;
outputs "Hello, from PowerShell!". Example is from the 2021 Threat Detection
Report by Red Canary.
Executor: command_prompt
ElevationRequired: False

Command:
powershell.exe -e #{obfuscated_code}

Command (with inputs):
powershell.exe -e JgAgACgAZwBjAG0AIAAoACcAaQBlAHsAMAB9ACcAIAAtAGYAIAAnAHgAJwApACkA...
```

### 4. Execução

```powershell
Invoke-AtomicTest T1059.001-17
```

Saída:

```Executing test: T1059.001-17 PowerShell Command Execution
Hello, from PowerShell!
...
Exit code: 0
Done executing test: T1059.001-17 PowerShell Command Execution
```
### 5. Localização do evento 

Refinando a busca para `eventID: 1` (criação de processo) e procurando pelo payload Base64 específico do teste, o evento correto foi localizado:

| Campo | Valor |
|---|---|
| `@timestamp` | Sep 14, 2026 @ 11:47:05.608 |
| `data.win.system.eventID` | 1 |
| `data.win.eventdata.parentCommandLine` | `"cmd.exe" /c powershell.exe -e JgAgACgAZwBjAG0AIAAoACcAaQBlAHsAMAB9ACcAIAAtAGYAIAAnAHgAJwApACkA...` |
| `rule.id` | 92032 |
| `rule.description` | Suspicious Windows cmd shell execution |
| `rule.level` | 3 |
| `rule.mitre.id` | T1087, T1059.003 |
| `rule.mitre.tactic` | Discovery, Execution |
| `rule.mitre.technique` | Account Discovery, Windows Command Shell |

O `parentCommandLine` confirma o Base64 idêntico ao mostrado no `-ShowDetails` do teste, validando que é de fato o evento gerado pela execução.

## Lições Aprendidas

- **Escopo mínimo de permissão como prática deliberada**: `Set-ExecutionPolicy -Scope Process` restringe a mudança à sessão ativa, evitando deixar a VM permanentemente mais permissiva a scripts após o teste — diferente de aplicar `-Scope LocalMachine`, que persiste indefinidamente.
- **Conflito Defender vs. ferramenta de simulação**: o Defender reagiu ao conteúdo dos arquivos de definição de teste (YAML), não à execução do ataque em si — sinal de que a camada de defesa endpoint está ativa e funcional, mesmo competindo com a ferramenta de simulação. Resolvido com `Add-MpPreference -ExclusionPath` no escopo da pasta do framework, decisão consciente e documentada por ser um lab isolado.
- **Falso positivo por correlação temporal**: eventos próximos no tempo não são necessariamente o mesmo evento. O evento inicial encontrado (`T1686`, Sysmon EID 11, regra T1105) tinha timestamp parecido mas era originado de outro processo (extração de atomics). A identificação correta exigiu comparar `eventID`, processo pai e conteúdo do comando — disciplina básica de análise que evita conclusões precipitadas.
- **Mapeamento MITRE pela cadeia de execução, não pelo rótulo do teste**: o Atomic Red Team executou o teste via `cmd.exe /c powershell.exe -e ...`. O Wazuh classificou o alerta como T1059.003 (Windows Command Shell) e T1087 (Account Discovery) — não como T1059.001 (PowerShell), a técnica nominal do teste. Isso evidencia que a regra 92032 reage ao padrão observado na cadeia de processo (cmd → powershell), não ao rótulo MITRE que o framework de simulação atribui ao teste.
- **Cobertura pronta do ruleset padrão**: diferente da validação anterior feita apenas com Sysmon (evento `net.exe START Wazuh` capturado sem regra correspondente), o padrão `-EncodedCommand` já é coberto nativamente pela regra 92032 do Wazuh, sem necessidade de regra customizada nesta rodada.
