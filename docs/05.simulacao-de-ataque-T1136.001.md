# Simulação de Escalonamento de Privilégio (T1136.001) e Investigação de Anomalias de Infraestrutura

## Objetivo

Simular a técnica MITRE ATT&CK T1136.001 (Create Account: Local Account) via Atomic Red Team, exercitando um cenário de Persistence/Privilege Escalation diferente das táticas já testadas (Execution/Discovery), e validar a resposta do Wazuh a esse comportamento. A investigação, inicialmente simples, revelou dois problemas reais de infraestrutura que precisaram ser diagnosticados e corrigidos antes de uma conclusão confiável ser possível.

## Ambiente

- **Windows 10** (192.168.56.20): Sysmon + Wazuh Agent ativos.
- **wazuh-manager** (192.168.56.5): Wazuh 4.14.
- **Técnica testada**: T1136.001-8 — "Create a new Windows admin user" (`net user /add` + `net localgroup administrators /add`).

## Processo

### 1. Execução inicial e obstáculo de idioma

A primeira execução do teste falhou no segundo comando:
```
net localgroup administrators "T1136.001_Admin" /add
Erro de sistema 1376. O grupo local especificado não existe.
```

O Atomic Red Team assume Windows em inglês (grupo `administrators`); no Windows em português o grupo se chama `Administradores`. Corrigido rodando manualmente:

```powershell
net localgroup Administradores "T1136.001_Admin" /add
```

### 2. Desvio de investigação: dessincronia de relógio

Ao buscar o alerta correspondente no Wazuh, nenhum resultado apareceu para o horário real do teste. A investigação em camadas eliminou, nesta ordem: problema de comunicação agente-manager (`ping`, `ossec.log` — normais), captura pelo Sysmon local (confirmada via Event Viewer, evento presente com `CommandLine` correto), e chegou ao root cause: o relógio da wazuh-manager estava atrasado em ~4h30 após um ciclo de Save State/retomada das VMs.

Diagnóstico:
```bash
timedatectl
date -u
```
Confirmado por comparação manual entre `date -u` e o horário UTC real (Curitiba UTC-3 + hora local).

Correção:
```bash
sudo timedatectl set-ntp true
sudo systemctl restart wazuh-manager
sudo systemctl restart wazuh-indexer
sudo systemctl restart wazuh-dashboard
```

**Lição:** alertas com timestamp incorreto por dessincronia de relógio comprometem a confiabilidade forense de qualquer investigação — a ordem cronológica dos eventos não pode ser confiada se os relógios das VMs não estão sincronizados. Save State prolongado é um gatilho conhecido para esse tipo de drift.

### 3. Repetição do teste e segundo obstáculo: lacuna de auditoria

Com o relógio corrigido, o teste foi refeito do zero (cleanup + `Invoke-AtomicTest T1136.001-8` + correção manual de grupo). O evento de **criação de conta** apareceu corretamente:

| Campo | Valor |
|---|---|
| `data.win.system.eventID` | 4738 |
| `rule.id` | 60110 |
| `rule.description` | User account changed |
| `rule.level` | 8 |
| `rule.mitre.id` | T1098 (Account Manipulation) |

Porém, o evento de **promoção ao grupo Administradores** (esperado como Event ID 4732) não aparecia em nenhuma busca no Wazuh. A investigação eliminou, nesta ordem: problema de correlação de campo na busca (checado com busca ampla por `eventID: 4732`, sem resultado) e captura pelo Sysmon (não aplicável — mudança de grupo é registrada no canal Security, não no Sysmon). Verificação direta no Event Viewer (Windows Logs → Security, filtrado por Event ID 4732) confirmou **zero eventos gerados** — a causa raiz não era o Wazuh, era o Windows nunca ter produzido o log.

Diagnóstico da causa raiz:
```powershell
auditpol /list /subcategory:* /r
```

A subcategoria de auditoria "Security Group Management" (gerência de grupo de segurança) não estava habilitada por padrão. Corrigida via GUID (evitando problema de tradução de nome no Windows em português):

```powershell
auditpol /set /subcategory:"{0CCE9237-69AE-11D9-BED3-505054503030}" /success:enable /failure:enable
```

### 4. Confirmação final

Com a auditoria habilitada, o teste foi executado uma terceira vez. O Event ID 4732 finalmente foi gerado e corretamente detectado:

| Campo | Valor |
|---|---|
| `data.win.system.eventID` | 4732 |
| `rule.id` | 60154 |
| `rule.description` | Administrators Group Changed |
| `rule.level` | 12 (mais alta severidade observada na sessão) |

## Lições Aprendidas

- **Um SIEM só é tão bom quanto os dados que chegam até ele.** O que parecia lacuna de detecção do Wazuh era, na verdade, ausência da fonte de dado na origem — a política de auditoria do Windows não gerava o evento. Regra de detecção não tem como atuar sobre um evento que nunca existiu.
- **Distinção entre problema de visibilidade e problema de detecção**, e a sequência correta de diagnóstico para diferenciá-los: confirmar existência do log na fonte (Event Viewer) antes de suspeitar do SIEM ou de suas regras.
- **Dessincronia de relógio invalida investigação forense.** Save State/pause prolongado de VMs é um gatilho comum para drift de horário; validar sincronização (`timedatectl`) deve ser parte do checklist pós-retomada de ambiente, não só quando algo já deu errado.
- **Diferenças de idioma do sistema operacional quebram scripts/comandos que assumem strings em inglês** (`administrators` vs `Administradores`, nomes de subcategoria do `auditpol`). Uso de GUIDs em vez de nomes textuais é mais robusto contra esse tipo de falha.
- **RIDs (SIDs) são únicos por criação de conta**, mesmo com nome de usuário idêntico — útil para diferenciar execuções repetidas de um mesmo teste ao longo de uma investigação.
- **Duas fontes de log distintas convivem no mesmo host** (Sysmon customizado vs. Windows Security Auditing nativo), cada uma com cobertura de eventos e configuração de auditoria próprias — nem todo comportamento relevante passa pelo Sysmon.
